# FruitScope 模型与训练报告

> **一句话**：在 787 张真实背景水果图（10 类）+ 416 张 `other` 负类上，冻结 MobileNetV3-Large 训一个线性头，再用"温度 + 阈值"标定，得到 **test 95.8%（10 类）/ 陌生图 81.3% 判为 other（11 类开集）** 的模型，直接驱动网站与终端演示。
>
> 数字来源可核对：权重与标定在 `ckpt/*_calib.json`，逐轮日志在服务器 `logs/*_train.log`，逐类指标在 `docs/E0*_test.json`，汇总在 `docs/experiments.md`。本文所有百分比都是这三处实测值，没有估算。

| 项目 | 结论 |

## 1. 场景与约束：为什么是"小模型 + 大 backbone 冻结"

**用户**：12–18 岁学生（生物/科学课、综合实践），次要使用者是教师与家长。他们要的不是"一个标签"，而是**可信、可学**的结果：既要知道"可能是什么"，也要知道"模型有多确定"，再配上知识卡片。

**约束条件**（这些约束直接决定了模型选型）：

1. 网站要部署在免费/低配平台，**CPU 推理、单图秒级、冷启动快**；
2. 只有 787 张训练图，**没有条件从头训或做大规模微调**；
3. 交互必须"稳"：用户可能拍任何东西，模型不能把番茄硬说成苹果；
4. 开发周期 1–2 周，需要可复现、可对比的实验流程。

**结论**：MobileNetV3-Large（官方 ImageNet 分类头下 5.5 M 参数，本项目替换分类头后总参数 2.98 M，ImageNet 预训练、BSD-3-Clause 许可）+ 替换分类头做迁移学习。DINOv3-ViT-S 保留为**加分对照**（同一测试集、同一口径），但不作为上线模型——ViT 在免费 CPU 上延迟与内存都不占优，且当前数据量下收益不确定。

一个刻意的取舍：**实现了三档分类头（linear / mlp / official），但实验只训练了 linear**。理由见 §3.3——787 张数据 + 冻结 backbone 已经到 95.8%，再堆头容量只会增加过拟合风险与调参面积。

## 2. 数据：先把"看起来 95%"里不该有的水分挤掉

### 2.1 来源与规模

| 项目 | 内容 |
| --- | --- |
| 主数据集 | Kaggle *Fruits and Vegetables Image Recognition*（作者 Kritik Seth），36 类 / 3825 张，约 2.17 GB |
| 用到的类别 | 数据集自带的 10 个水果类：apple、banana、grapes、kiwi、mango、orange、pear、pineapple、pomegranate、watermelon（**没有草莓**，不做"等价替换"） |
| 取用量 | 10 类合计 **1033 张** |
| 图像特点 | Bing 检索采集，角度/光照/背景多样（真实场景背景，非纯色背景棚拍）——这点很重要，纯背景数据集训出来的模型一换背景就崩 |
| 每类原始量 | 约 86–95 张，量非常小，必须靠增强 |

原计划里的 Kaggle *Fruits-360*（只进训练集、不进验证/测试）最终**没有启用**（`--fruits360-per-class 0`）。原因：Fruits-360 是统一装置、视频逐帧采集，相邻帧近乎重复，且背景高度一致，混进来会让模型学到"背景"而不是"水果"；在只有 1–2 周、又要保证评估可信的前提下，先保证"数据干净 + 口径统一"比"数据更多"更重要。

### 2.2 去重：这是整个项目最关键的一次数据修正

官方 `train/`、`validation/`、`test/` 三个目录里有**同一张图（甚至同一张图的不同文件名）重复出现**。直接合并使用，等于把测试图塞进训练集。

- 实测：1033 张里 **246 张重复（23.8%）**，去重后 787 张；
- 手段：自写 pHash（`src/dedup.py`，纯 numpy，不依赖 `imagehash`）——灰度 → 32×32 → DCT-II → 取 8×8 低频 → 中位数二值化成 64 bit；
- 近邻检索用 **banding（鸽笼原理）**：把 64 bit 切成 `threshold+1=9` 段，汉明距离 ≤ 8 的两张图至少有一段完全相同，因此只在同段候选里比对，避免 O(n²) 全量比较；
- 划分后再做一次**跨划分泄漏复查**：两份 splits 都是"未发现近重复"。

如果不做这一步，test 上的数字会虚高一大截，而且**所有实验之间的对比都会失真**——这是"先修数据再加模型"的典型例子。

### 2.3 划分

| splits 文件 | 用途 | 去重后总量 | train / val / test |
| --- | --- | --- | --- |
| `data/splits.json` | 10 类（E01 / E05） | 787 | 551 / 118 / 118 |
| `data/splits_other.json` | 11 类窄口径 other（E02） | 1172 | 820 / 176 / 176 |
| `data/splits_other_broad.json` | 11 类宽口径 other（E03 / E04） | 1203 | 843 / 180 / 180 |

- 划分比例 70/15/15，`seed=42`，**同一份 splits 文件被所有实验共用**（否则指标不可比）；
- 测试集只看一次：模型选择与早停都用 **val 的 macro-F1**，不用 test；
- 不用官方 test 的原因：官方 test 每类约 10 张，10 类只有约 100 张，**错一张就是 1%**，85% 的 95% CI 约 ±7%，根本撑不起"结论"。

### 2.4 `other` 负类：窄口径 → 宽口径

要回答"这是不是水果"，光有 10 个正类不够，必须给模型一个 `other` 负类。这里踩了一个大坑（详见 §7.4）：

| 口径 | 来源 | 数量 | 训练集 other 占比 | OOD→other |
| --- | --- | --- | --- | --- |
| 窄口径（E02） | 17 个根茎类蔬菜目录 × 26 | 442（去重后 385） | 32.8% | **28.9%** |
| 宽口径（E03/E04） | 26 个目录 × 17，**含番茄/黄瓜/甜椒/辣椒/茄子/柠檬** | 442（去重后 416） | 34.6% | **72.0% → 81.3%** |

四条约束同时成立才允许加 `other`：

1. **不能让它主导**：`scripts/01_data_prepare.py` 会打印最大/最小类比与 other 占比，>40% 直接告警；
2. **开 `--weighted-sampler`**：11 类训练全部用逆频率采样，否则 other 会把水果类的判决边界拉偏；
3. **和正类一起做 70/15/15**（同一个 `split_class`），并参与 pHash 去重与跨划分泄漏检查；
4. **留一部分做 OOD 测试**：宽口径把"蔬果难分"的类别教成 other 后，OOD 测试集不能再拿同一批图，必须用 `data/manifest_other_broad.csv` 排除已占用图片（`02_build_ood.py --exclude-from`）。

### 2.5 OOD 测试集（开集评估）

`data/ood`：**225 张 / 9 类**——tomato、cucumber、bell pepper、capsicum、paprika、chilli pepper、jalepeno、eggplant、lemon（数据集里没有 avocado，自动跳过）。

它衡量的是**上线真正会发生的事**：用户拍了一个"我们没训练过的东西"。

- 窄口径 other 训练时这些类别完全没见过 → 纯开集；
- 宽口径训练时它们部分进入 other，但 OOD 只用**未被占用**的图片 → 保证不重叠、指标可信。

### 2.6 增强与预处理（训练 / 评估 / 上线三件套）

| 环节 | 配置 | 为什么这么定 |
| --- | --- | --- |
| 训练裁剪 | `RandomResizedCrop(224, scale=(0.6,1.0), ratio=(0.8,1.25))` | 默认 `scale=(0.08,1.0)` 会把单主体水果裁成"一片果皮/纯背景"，模型学不到东西 |
| 翻转 | 仅左右翻转 `p=0.5` | 水果有天然朝向，**不做上下翻转** |
| 仿射 | `RandomAffine(15°, translate=0.05)`，`fill=(124,116,104)` | 用数据集中位色填充，避免纯黑边角引入训练/推理都不存在的伪域 |
| 颜色 | `ColorJitter(0.2, 0.2, 0.2, 0.02)` | 手机拍照色温差异大，hue 只给 0.02（改太狠会把橙子变青柠） |
| 正则 | `RandomErasing(p=0.25, scale=(0.02,0.15))` | p 从 0.5 降到 0.25、面积上限 15%，别把主体擦没 |
| 评估/推理 | `Resize(short=256)` → `CenterCrop(224)` → `Normalize(ImageNet)` | **不是** `Resize((224,224))`，否则长宽比被压扁 |
| 读图 | `load_image()`：EXIF 摆正 → 转 RGB → 长宽比 >2.5 先 pad 成方形 | 手机照片不摆正会整张躺倒；PNG 带 alpha / 灰度 / CMYK 统一 3 通道；长截图直接 CenterCrop 会裁掉主体 |

关键约定：**训练、评估、推理共用 `src/transforms.py` 这一份**，网站端不许另写一套预处理——像素级不一致是"训练 95%、线上 60%"的头号原因。

## 3. 模型结构

### 3.1 整体结构

```
输入 224×224×3 (RGB, ImageNet 归一化)
   │
   ▼
MobileNetV3-Large backbone（torchvision, ImageNet 预训练）
   │   features: 17 个 block（InvertedResidual + SE + Hardswish）
   │   动态量化友好的 Hardswish + SE
   ▼
全局平均池化 → 960 维特征
   │
   ▼
分类头：nn.Linear(960, C)         C=10 或 11（11 类时多一个 other）
   │
   ▼
logits → softmax(z / T) → top-k + 阈值判决 → 三态文案
```

| 指标 | 10 类 | 11 类 |
| --- | --- | --- |
| 总参数 | 2,981,562 | 2,982,523 |
| 分类头参数 | 9,610（960×10+10） | 10,571（960×11+11） |
| 冻结阶段可训练参数 | **9,610（0.32%）** | **10,571（0.35%）** |
| checkpoint 体积 | 约 12 MB | 约 12 MB |

> 参数量取自训练日志 `num_params={'total': 2981562, 'trainable': 9610, 'head': 9610}`，不是估算。

### 3.2 三档分类头（实现了三档，实验只用了 A）

| 档位 | 结构 | 参数量 | 是否采用 |
| --- | --- | --- | --- |
| A `linear` | `Linear(960→C)` | 9.6 K | ✅ **全部实验都用它** |
| B `mlp` | `Linear(960→256) → BN1d → Hardswish → Dropout(0.3) → Linear(256→C)` | ≈249 K | 实现并可通过 `--head mlp` 调用，未做实验 |
| C `official` | `Linear(960→1280) → Hardswish → Dropout(0.2) → Linear(1280→C)`（官方分类头结构） | ≈1.24 M | 同上 |

代码在 `src/model.py`，`build_model(head=...)` 一行切换；`build_from_checkpoint()` 依据 checkpoint 里存的 `head.type` 重建结构，所以三档权重可以共存、互不干扰。

### 3.3 为什么最终只要 A 档

- 787 张数据、冻结 backbone，**特征本身来自 ImageNet 预训练，已经很"够用"**：线性头就到 test 95.76%；
- B/C 档多出来的参数量在这点数据上只会拉大"训练集拟合 vs 验证集"的缝隙，而验证集只有 118–180 张，**调不出可信的差异**（错一张就是 0.5–0.8 个点）；
- 评审关注"理解取舍"，所以这里的取舍是明确写下来的：**当前阶段加头容量不是瓶颈，解冻与负类设计才是**（§4.4 的 E03→E04 印证了这一点）。

### 3.4 checkpoint 契约：一个文件装下所有推理约定

推理端不能"猜"任何东西，所以训练完把全部约定写进 checkpoint：

| 字段 | 作用 |
| --- | --- |
| `arch` / `head{type,hidden,dropout}` | 重建网络结构（不依赖代码里的默认值） |
| `classes` | 类别顺序（**softmax 下标 → 类名的唯一真相**） |
| `img_size` / `mean` / `std` | 预处理参数随权重一起走，换机器不会错 |
| `temperature` | 温度校准值（`src/calibrate.py` 回写） |
| `threshold` / `threshold_meta` | 拒识阈值与标定依据（score=msp、FRR、样本量） |
| `openset` | OOD 上的预测分布（other 占比、被硬判成水果的比例） |
| `val` / `test` | 训练时的指标快照，便于线上对比"有没有漂" |
| `args` / `env` | 全部超参与 torch/CUDA/GPU 版本，复现时先看这里 |
| `state_dict` | 权重 |

`src/predict.py::Predictor` 只做三件事：按 checkpoint 重建模型 → 用 checkpoint 的预处理读图 → `softmax(logits / T)` 后取 top-k 并比阈值。**网站、终端演示、评估脚本共用这一个类**，因此"演示里的数字"和"实验里的数字"必然一致。

### 3.5 三态输出（模型 -> 产品）

```python
if probs.max() < threshold:      "未识别为支持的水果，请换一张更清晰、主体更完整的照片"   # 拒识
elif top1 == "other":            "这不是我认识的水果（支持苹果/香蕉/…/西瓜）"            # 开集
else:                            f"可能是{中文名}"                                     # 命中
```

这一段是模型与产品的接口：**模型不只输出标签，还输出"我不确定"和"这不是水果"两种可解释状态**。

## 4. 训练过程

### 4.1 两阶段策略

**阶段一（默认，所有 run 都跑）：冻结 backbone，只训头**

- `freeze_backbone()` 把 `features` 全部 `requires_grad=False`；
- **每个 epoch 的 `model.train()` 之后必须重新调用 `set_frozen_bn_eval()`**，把冻结 block 的 `BatchNorm2d` 强制 `eval()`——否则 BN 的 running stats 会继续漂移，"冻结"等于没冻结（这是 v1 的 bug，见 §7.2）；
- 优化器只注册可训练参数，并按"是否衰减"分四组：head/backbone × (weight decay / no decay)，**BN 权重与 bias 不做 weight decay**；
- 学习率：head `1e-3`，cosine annealing，`T_max` = 本阶段总 epoch；
- 损失：`CrossEntropyLoss(label_smoothing=0.1)`；
- 早停：监控 **val macro-F1**（不是 acc），`patience=5`，保存最优权重。

**阶段二（条件触发）：解冻 `features[-3:]`**

- 从阶段一最优权重出发，`model.features[14:]` 三个 block 解冻（MobileNetV3-Large 共 17 个 block）；
- **重建优化器**（head `1e-3` / backbone `1e-4`）与新的 cosine `T_max=15`，否则学习率会按阶段一的进度直接归零；
- 仍然按 val macro-F1 早停，且阶段一的最优分作为阶段二的起点基线（不允许"解冻后变差还覆盖掉好权重"）。

### 4.2 超参（`config.DEFAULTS`，全部写进 checkpoint）

| 项 | 值 |
| --- | --- |
| arch / head | `mobilenet_v3_large` / `linear` |
| epochs | 30（阶段一）/ 15（阶段二） |
| batch_size | 32（551 张 ≈ 18 step/epoch） |
| lr_head / lr_bb | 1e-3 / 1e-4 |
| optimizer / weight_decay | AdamW / 1e-4（BN、bias 不衰减） |
| label_smoothing | 0.1 |
| scheduler | CosineAnnealingLR，`T_max`=阶段 epoch 数 |
| patience | 5（按 val macro-F1） |
| seed | 42（`set_seed` + DataLoader `generator` + `worker_init_fn`） |
| num_workers | 8 |

### 4.3 实验矩阵（5 组，同一划分口径）

| run | 数据 | 冻结策略 | 训练轮数（实际） | val macro-F1 | test acc | macro-F1 | Top-3 | OOD→other |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| E01 | 10 类 | 全程冻结 | 16（ep11 最优，早停） | 0.9354 | **0.9576** | 0.9572 | 0.9746 | 无 other 类 |
| E02 | 11 类窄口径 | 全程冻结 | 22（ep17 最优） | 0.9151 | 0.8920 | 0.8872 | 0.9773 | 28.9% |
| E03 | 11 类宽口径 | 全程冻结 | 14（ep9 最优） | 0.8670 | 0.8667 | 0.8680 | 0.9778 | 72.0% |
| **E04** | **11 类宽口径** | **解冻 [-3:]** | 14 + 8（stage2 ep3 最优） | **0.8997** | **0.9056** | **0.8990** | **0.9833** | **81.3%** |
| E05 | 10 类 | 解冻 [-3:] | 16 + 5 | 0.9354 | 0.9576 | 0.9572 | 0.9746 | 无 other 类 |

三段真实日志摘录（可对照 `logs/`）：

```text
[stage1] ep01/30 loss=2.0356 val_acc=0.7627 val_f1=0.7482 lr=9.97e-04 (6.9s)   # E01
[stage1] ep11/30 loss=0.7520 val_acc=0.9407 val_f1=0.9354 lr=7.03e-04 (6.4s)
[stage1] 早停：val macro-F1 连续 5 轮无提升
test: acc=0.9576 95%CI=[0.9046, 0.9818] macro_f1=0.9572 top3=0.9746

[stage1] ep09/30 loss=0.8134 val_acc=0.8778 val_f1=0.8670 lr=7.94e-04 (8.4s)   # E03
[stage1] 早停：val macro-F1 连续 5 轮无提升

阶段二：解冻 features[14:]（3 个 block）                                          # E04
[stage2] ep03/15 loss=0.6778 val_acc=0.9056 val_f1=0.8997 lr=9.05e-04 (7.6s)
[stage2] 早停：val macro-F1 连续 5 轮无提升
test: acc=0.9056 95%CI=[0.854, 0.9402] macro_f1=0.8990 top3=0.9833
```

读日志能看出三件事：

1. **收敛很快**：E01 第 1 轮 val_f1 就 0.7482，第 11 轮到 0.9354，之后进入平台期——预训练特征 + 小数据，训头就是最省的做法；
2. **早停真的在起作用**：三个 run 都在 14–22 轮停下，没有把 30 轮跑满，避免了后期在 118 张验证集上继续"拟合噪声"；
3. **E03→E04 的收益来自解冻而不是更多轮数**：stage2 第 3 轮就把 val_f1 从 0.8670 拉到 0.8997，一次跳 3.3 个点。

### 4.4 时间成本

单卡 RTX 3090：**6–9 s/epoch**（551–843 张，18–27 step）。E01 约 2 分钟、E04 约 3 分钟；加上数据准备、OOD 构建、校准与评估，**整个 5 组矩阵 < 30 分钟**。这意味着可以放心做"多跑几组对比"而不是"一次调参赌运气"。

## 5. 校准与开集拒识：让"置信度"变成能用的东西

### 5.1 温度标定（`src/calibrate.py`）

在 val 上用 LBFGS 拟合单一温度 T，最小化 NLL（优化 `log T` 保证 T>0），然后回写 checkpoint：

| run | T | ECE(val) 前 → 后 | ECE(test) |
| --- | --- | --- | --- |
| E01 | 0.4330 | 0.2137 → 0.0556 | 0.0422 |
| E02 | 0.5194 | 0.2004 → 0.0527 | 0.0490 |
| E03 | 0.4856 | 0.2244 → 0.0581 | 0.0748 |
| E04 | 0.5121 | 0.1764 → 0.0359 | 0.0454 |
| E05 | 0.4330 | 0.2137 → 0.0556 | 0.0422 |

### 5.2 为什么 T < 1（这里容易被误解，值得单独讲）

常识里"小数据微调模型过自信，T 应该 > 1"。我们实测出来是 **T≈0.43–0.52 < 1，也就是要"提亮"概率**。原因有两个，都是自己代码里的选择造成的：

1. **`label_smoothing=0.1`**：10 类时正类目标被压到约 `1-0.1+0.1/10 = 0.91`，模型被训练成"最多只敢说 0.9 出头"，而实际准确率是 0.9576 → **系统性欠自信**（标定前的 ECE 0.21 意味着平均置信度比准确率低约 0.21，即置信度≈0.75 对应准确率 0.96）；
2. **早停 + cosine 未走完**：停在 11/30 轮，logit 尺度还没长到饱和。

所以 T<1 不是异常，而是"标定在纠正我们自己注入的偏差"。这条经验直接写进了 `src/calibrate.py` 的注释与告警：**T 命中 1e-3 或 1e3 边界才说明模型有问题，T<1 但 ECE 明显下降是正常结果**。

### 5.3 拒识阈值（MSP，target FRR ≤ 5%）

在 val（ID）与 `data/ood`（OOD）上扫阈值，在**正常样本误拒率 ≤ 5%** 的约束下最大化陌生图拒识率：

| run | 阈值 | OOD 被阈值拒识 | ID 误拒 | 说明 |
| --- | --- | --- | --- | --- |
| E01 | 0.5099 | 24.0% | 4.24% | 10 类没有 other，只能靠阈值兜底 |
| E02 | 0.4590 | 19.6% | 4.55% | 有 other，但模型不会用 |
| E03 | 0.4514 | 8.4% | 3.33% | other 开始吸收陌生图（72%），阈值退居二线 |
| E04 | 0.4789 | 2.7% | 4.44% | 81.3% 已被 other 吸收，阈值只处理"极端陌生" |

**"阈值不能手填"是硬结论**：常见做法是拍一个 0.6，但实测标定值是 0.45–0.51，**手填 0.6 等于永不拒识**——线上就会把番茄硬说成苹果。所以 `config.CONF_THRESHOLD` 保持 `None`，一切以 `calibrate.py` 写进 checkpoint 的值为准。

### 6.3 坏案例（题目硬性要求：至少一个效果不理想的案例 + 分析）

**① 柠檬 → 橙子，置信度 0.999（模型最"自信"的错误）**

```
lemon_0001.png: 识别 -> 橙子(orange) 0.964 | 猕猴桃(kiwi) 0.010
lemon_0010.jpg: 识别 -> 橙子(orange) 0.999
```

- **现象**：宽口径训练时 lemon 的 17 张图确实被教成了 `other`，但 OOD 里另外 23 张柠檬仍然被判成橙子，而且置信度极高；
- **分析**：① 橙子/柠檬在 ImageNet 特征空间里本来就挨着（黄色、椭圆、高光位置相似），线性头只能切一刀，切不开；② `other` 是个"杂类垃圾桶"——26 个目录 416 张图混成一个类，中心极其发散，一张柠檬离 `other` 的"平均方向"远、离 `orange` 的簇中心近；③ 每类只有 17 张，远不足以把这个边界教出来；
- **处理**：不掩盖，直接当成"已知局限"写进演示脚本（`demo/manifest.json` 里特意保留一条 `misclass`），并在文档里给出两条可选方案（§8）。

**② 芒果：F1 只有 0.667（类内一致性最差的类别）**

- **现象**：11 张测试芒果，8 张对、2 张判成梨、1 张判成橙子；反向也有 1 张梨被判成芒果；
- **分析**：芒果有青皮/黄皮、长短差很大的品种，青芒果和梨在"形状 + 颜色 + 高光"上高度重叠；训练集芒果只有 54 张，且都是商品图统一摆拍；
- **处理**：这是**数据问题而不是结构问题**——加头容量（§3.2 B/C 档）不会解决"同类长得不像"，加数据/加针对性增强（更强的 hue jitter、局部遮挡）才有效。

**③ 番茄被判"拒识"而不是"other"（0.359 < 0.479）**

```
tomato_0003.jpg: 拒识 -> 其他 0.359 | 苹果 0.339
```

- **现象**：模型"感觉不对"但没有把 `other` 顶到第一；
- **分析**：这是**双保险生效**的样子——阈值这条线比 other 类更敏感，对"其他也像、水果也像"的模糊样本会先拦下来；对产品来说这是可接受（甚至更好）的结果：用户看到的是"未识别为支持的水果，请换一张…"，而不是一个错误的高置信答案；
- **代价**：阈值调高会同时拒掉正常水果（E04 在 FRR=4.4% 处取 0.479，再高就会误伤）。

**④ 一次失败的尝试：窄口径 other 几乎没用**

| 口径 | OOD 判成 other | 被硬判成水果 | 主要错误去向 |
| --- | --- | --- | --- |
| 窄口径（17 个根茎类） | 28.9%（65/225） | **71.1%** | apple 61、banana 28、orange 27 |
| 宽口径（26 个含蔬果难分） | 72.0%（162/225） | 28.0% | orange 27、apple 11 |
| 宽口径 + 解冻 | **81.3%（183/225）** | 18.7% | orange 23、apple 6 |

**分析**：负类的"教学内容"决定了边界在哪。只教根茎类（土豆/胡萝卜），模型学到的"不是水果"= "土色、长条形、粗糙表面"，而番茄/柠檬/黄瓜这类**长相接近水果的负类从未出现**，模型没有任何理由拒绝它们——于是按最近的簇硬判成 apple/orange。这条结论是整个项目里最有价值的一次"负结果"。

### 6.4 上线该选哪个：E01 还是 E04

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 用户基本只拍这 10 种水果 | E01（10 类） | 水果准确率最高 95.8%，误拍靠 MSP 阈值兜底（24% 拦截 + 4.2% 误拒） |
| 用户可能拍任何东西，宁可说"不认识" | **E04（宽口径 + 解冻）** | 81.3% 陌生图被正确归为 other，水果准确率 91.5% |

产品实际选了 **E04**：面向学生的场景里，"把番茄说成苹果"比"说一句不认识"伤害大得多；1.7 个点的水果准确率换 52 个点的开集鲁棒性，这笔交易是划算的，而且这个取舍本身就在演示里明明白白地演给用户看。

## 7. 遇到的困难（按"踩坑 → 诊断 → 处理 → 结论"记）

### 7.1 官方划分里有重复图，测试集被"泄漏"进训练集

- **现象**：第一次按官方 `train/val/test` 直接训，val 指标异常好，怀疑数据有问题；
- **诊断**：算 pHash，发现同一张图在三个目录里以不同文件名重复出现，汉明距离 0；1033 张里 246 张重复（23.8%）；
- **处理**：合并 → pHash 去重（阈值 8）→ 重新 70/15/15 划分 → 划分后再做一次跨划分泄漏复查；不引入 `imagehash`，自己用 numpy 写（含 banding 加速，避免 O(n²)）；
- **结论**：**"先修数据，再谈模型"**。这一步不做，后面所有对比都是假的。

### 7.2 冻结 backbone 后 BN 仍在更新，"冻结"等于没冻结

- **现象**：计划书 v1 的训练循环里已经 `requires_grad=False`，但 val 曲线抖得厉害，且解冻前后差别很小；
- **诊断**：`model.train()` 会把**所有** BN 层切回 train 模式，running mean/var 继续被 batch 统计量改写——参数没变，但归一化统计量在漂；
- **处理**：每个 epoch 的 `model.train()` 之后再调用 `set_frozen_bn_eval(model, unfreeze_last)`，只允许解冻 block 的 BN 处于 train；
- **结论**：**"冻结"必须每轮重做**，还要区分"冻结 block 的 BN"与"解冻 block 的 BN"。这是本项目最容易复现失败的一处，已写进 README 的"关键约定"。

### 7.3 拍脑袋的阈值 0.6，线上永不拒识

- **现象**：按经验（也是很多教程的写法）手填 `CONF_THRESHOLD=0.6` 时，模型输出根本碰不到这条线，连番茄都被高置信判成 apple；
- **诊断**：label smoothing 把概率压平（§5.2），val 上 95% 正常样本的最高概率都在 0.5 左右，0.6 是个永远达不到的门槛；
- **处理**：`config.CONF_THRESHOLD=None`，一律由 `src/calibrate.py` 在 FRR≤5% 约束下扫出来并写进 checkpoint；
- **结论**：**阈值是数据属性，不是超参**。五个 run 标出来是 0.45–0.51，差异本身就说明"抄一个数字"不可行。

### 7.4 窄口径 other：加了负类，开集能力反而没提升

- **现象**：E02 加了 442 张根茎类蔬菜当 `other`，OOD 只有 28.9% 判成 other，其余 71% 被硬判成 apple（61 张）、banana（28 张）、orange（27 张）；
- **诊断**：看 OOD 预测分布才明白——负类教的是"土豆/胡萝卜长什么样"，而 OOD 是番茄/柠檬/黄瓜，**长相接近水果的负样本从未出现在训练里**，模型没有依据拒绝它们；
- **处理**：改宽口径——把蔬果难分的类别（tomato/cucumber/bell pepper/capsicum/paprika/chilli pepper/jalepeno/eggplant/lemon）也放进 `other`，OOD→other 从 28.9% 升到 72.0%；
- **结论**：**负类的"教学内容"决定边界位置**。这是我觉得最有价值的一次负结果：不是模型不够大，而是没教对东西。

### 7.5 宽口径的新麻烦：OOD 与 other 用同一批图 → 指标虚高

- **现象**：宽口径第一版跑出来 OOD→other 高得可疑；
- **诊断**：`other` 从 26 个目录采样，`data/ood` 又从同样的目录采样，**图片可能重叠**（同一张图既在训练又在 OOD）；
- **处理**：`01_data_prepare.py` 把 other 的每个来源文件写进 `data/manifest_other_broad.csv`；`02_build_ood.py --exclude-from` 在构建 OOD 时排除这些文件，保证两张清单不相交；
- **结论**：一旦"训练里出现过的类"被拿去做开集测试，就**必须按图片而不是按类别**排除，否则指标没有意义。

### 7.6 类失衡：other 占训练集 34.6%，会主导损失

- **现象**：11 类第一版（未加权）other 类 recall 很高，但水果类 recall 掉；
- **处理**：`--weighted-sampler`（逆频率采样）+ `drop_last`（防 `BatchNorm1d` 在最后一个 batch=1 时崩）+ 训练前打印 other 占比，>40% 告警；
- **结论**：负类不是"越多越好"，配额要和"不主导"一起设计。

### 7.7 验证集只有 118–180 张，指标抖动大

- **现象**：同一份权重换一批增强序列，val acc 能抖 2–3 个点；
- **处理**：早停看 **macro-F1**（对小样本与类间不均衡更稳）、`patience=5`、**test 只在最后用一次**、报告一律给 95% Wilson CI；
- **结论**：小验证集上"挑最好的 epoch"很容易变成挑噪声，所以要限制搜索空间（早停 + 只看 val + 不碰 test）。

### 7.8 解冻不是万能药：10 类完全没收益

- **现象**：E05（10 类 + 解冻 3 个 block）与 E01 的 val/test 指标**完全一致**，都是 ep11/val 0.9354 早停；
- **诊断**：冻结特征已足够支撑 10 类线性可分；解冻的额外自由度只在"类别更多、边界更糊"时才有用；
- **处理**：保留解冻作为**条件动作**（仅在 11 类出现瓶颈时触发），不做默认流程；
- **结论**：E03→E04（acc +3.9、OOD→other +9.3）证明解冻要用在刀刃上，而不是无脑加。

### 7.9 工程环境问题（都是真实挡过路的）

| 问题 | 处理 |
| --- | --- |
| 服务器没装 matplotlib，混淆矩阵保存报错 | 异常兜底：降级写成 `cm_*.txt`，不中断训练（日志里能看到 `[warn] 未安装 matplotlib…`） |
| SSH 隧道（cpolar）间歇掉线 | `tar + scp` 带重试的同步脚本；训练用 `nohup` + `tee` 落盘，掉线不影响训练 |
| 本地 Windows 无 GPU | 合成数据集端到端冒烟测试（`tests/smoke_test.py`，3 类 × 24 张，跑 准备→训练→评估→校准→推理），保证代码链路不断 |
| 随机性控制 | DataLoader 传 `generator` + `worker_init_fn`，`set_seed(42)` 同时管 torch/cuda/numpy/random，`cudnn.deterministic=True` |
| 换机器加载 checkpoint | checkpoint 写入 `env`（torch/torchvision/CUDA/GPU 名）与 `img_size/mean/std`，推理端以 checkpoint 为准并给出不一致告警 |

### 7.10 上线一致性：训练 95%、线上 60% 的典型原因

手机照片会带来 EXIF 旋转、PNG alpha、极端长宽比、超大分辨率四个坑。处理集中在 `load_image()`：EXIF 摆正 → 转 RGB → 长宽比 >2.5 先 pad 成方形，再统一走 `build_eval_transform()`。

更关键的是**只有一份预处理**：训练、评估、网站、终端演示全部 `import` 同一份 `src/transforms.py`，且 `Predictor` 用 checkpoint 里的 `img_size/mean/std`，不读代码默认值。

| 不足 | 影响 | 计划 |
| --- | --- | --- |
| `other` 是单一"杂类"（26 类 416 张混成 1 类） | 中心发散，柠檬这类"像水果的负类"仍被判成 orange（10.2%） | ① 二分类门控（fruit / non-fruit）+ 10 类细分类的**级联**；② 或把 other 拆成 2–3 个语义子类 |

## 10. 与产品侧的衔接

1. **单一推理入口**：网站 / 终端演示 / 评估脚本都调用 `src/predict.py::Predictor`，没有第二套推理逻辑，页面上的置信度、Top3、拒识判断与本文档数字同源；
2. **三态文案**（命中 / other / 拒识）直接来自模型输出，前端只按状态渲染，不需要自己编话术；
3. **演示可复现**：`scripts/05_build_demo.py` 只用 test/OOD 挑图并现场推理判定，`scripts/demo.py` 逐张重放；换 checkpoint 后重新生成素材，保证"演的就是当前模型"；
4. **失败透明**：柠檬→橙子这条已知局限被**固定写进演示素材**（`misclass`），不靠挑好看的图来美化效果。

**关于 AI 辅助**：代码骨架、计划书与文档整理使用了 AI 辅助；而数据清洗口径、负类设计、解冻策略、阈值标定方式、坏案例取舍，均由本项目实测数据驱动——每组实验都在 4×RTX 3090 服务器上真实训练并保留日志，文中每个数字都能在上述日志与 JSON 中查到。
